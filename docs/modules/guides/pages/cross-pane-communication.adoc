= Cross-Pane Agent Communication
:description: Enable AI agents running in separate Zellij panes to discover each other, read terminal output, query state, and ask questions across sessions.

When running multiple AI agent sessions side by side in Zellij, each session operates in isolation.
One agent cannot see what another is doing, which means the user must manually relay information between panes.
cc-deck solves this with an MCP server that exposes cross-pane communication tools, letting agents collaborate without human intermediation.

The MCP server (`cc-deck mcp serve`) provides four tools that any MCP-capable agent can call: listing active sessions, reading another session's terminal output, querying structured state, and asking another agent a question directly.

== Getting Started

Cross-pane communication is set up automatically when you install the cc-deck plugin.
The install command registers the MCP server in each detected agent's configuration so the cross-pane tools become available immediately.

[source,bash]
----
cc-deck config plugin install
----

For Claude Code, this adds a `cc-deck` entry to the project `.mcp.json` file that launches `cc-deck mcp serve` as a stdio-based MCP server.
Codex and OpenCode receive equivalent configuration entries in their respective configuration files.

No additional setup is required.
Once installed, any agent session running inside a Zellij instance with the cc-deck plugin can call the four cross-pane tools.

== How It Works

Each agent session that uses cross-pane tools spawns its own `cc-deck mcp serve` process.
The MCP server communicates with the agent over stdio (standard input and output), following the standard MCP transport protocol.

When a tool is called, the MCP server sends a pipe message to the cc-deck Zellij plugin, which has direct access to all pane metadata, scrollback buffers, and session state.
The plugin processes the request and sends the response back through the pipe.
This architecture means that sessions which never use cross-pane tools incur zero overhead: no background processes, no polling, no network listeners.

The communication flow looks like this:

[source,text]
----
Agent --> MCP Server (stdio) --> Zellij pipe --> cc-deck plugin --> response
----

All communication happens within a single Zellij instance on the local machine.
There is no cross-machine or network-based communication.

== MCP Tools

=== cc_deck_sessions

Discovers all active agent sessions in the current Zellij instance.
This is the starting point for any cross-pane interaction, since you need to know what sessions exist before you can read their output or ask them questions.

The tool takes no parameters and returns a JSON array of session objects.
Each object includes the session name, agent type (Claude Code, Codex, or OpenCode), activity state, working directory, git branch, current topic, recent tools used, modified files, and a project summary.

**Example use cases:**

* An agent starting a new task checks what other sessions are already working on to avoid duplicate effort.
* A coordinating agent surveys all sessions to decide which one to ask for help with a specific file or module.
* An agent verifies whether another session is idle before attempting to ask it a question.

**Returned fields for each session:**

[cols="1,3"]
|===
| Field | Description

| `name`
| The display name of the session (used as identifier in other tool calls)

| `pane_id`
| Zellij pane identifier (use for disambiguation when names conflict)

| `agent`
| Agent type: `claude`, `codex`, or `opencode`

| `state`
| Activity state: `idle`, `working`, `waiting`, or `done`

| `cwd`
| Current working directory

| `branch`
| Git branch name

| `topic`
| First 100 characters of the most recent user prompt

| `project_summary`
| Summary derived from the project's CLAUDE.md file

| `recent_tools`
| Last 10 tool names from hook events

| `modified_files`
| Files with uncommitted git changes

| `paused`
| Whether the session is paused
|===

=== cc_deck_read_scrollback

Reads the terminal scrollback buffer from another session's pane.
This provides raw observation of what a session has been doing without disrupting it.

**Parameters:**

[cols="1,1,1,3"]
|===
| Name | Required | Default | Description

| `session`
| yes
| -
| Session display name or pane ID

| `lines`
| no
| 50
| Number of lines to read (1 to 500)
|===

The tool returns plain text containing the last N non-empty lines from the target pane's terminal buffer.

**Example use cases:**

* An agent reads the last 30 lines from a session that just finished to understand what it accomplished.
* A debugging agent reads scrollback from a session that encountered an error to diagnose the problem from its own context.
* An agent checks another session's recent output before deciding whether to ask it a follow-up question.

=== cc_deck_session_state

Queries structured state for a single session.
This provides richer, machine-readable information compared to raw scrollback, making it suitable for programmatic decision-making.

**Parameters:**

[cols="1,1,3"]
|===
| Name | Required | Description

| `session`
| yes
| Session display name or pane ID
|===

The tool returns a JSON object with the session's git state, recent tool activity, and activity timeline.

**Returned fields:**

[cols="1,3"]
|===
| Field | Description

| `name`
| Session display name

| `pane_id`
| Zellij pane identifier

| `cwd`
| Working directory

| `branch`
| Current git branch

| `git_diff`
| Summary of uncommitted changes (equivalent to `git diff --stat`)

| `modified_files`
| List of changed files

| `recent_commits`
| Last 5 commit messages

| `recent_tools`
| Recent tool names with timestamps

| `topic`
| Current topic from the most recent prompt

| `activity_timeline`
| Recent state transitions with timestamps
|===

**Example use cases:**

* An agent checks another session's git diff to understand what files it has modified before making changes to the same codebase.
* A coordinating agent reviews recent tool usage across sessions to understand which one has the most relevant context for a question.
* An agent reads the activity timeline to determine how long another session has been idle.

=== cc_deck_ask

Asks another agent a question and receives a response.
This is the most powerful cross-pane tool: it enables true agent-to-agent consultation where each agent reasons from its own full context.

The question is injected into the target session's input when it is idle.
The target agent processes the question, writes its response to a temporary file, and the response is returned to the calling agent.

**Parameters:**

[cols="1,1,1,3"]
|===
| Name | Required | Default | Description

| `session`
| yes
| -
| Target session display name or pane ID

| `question`
| yes
| -
| Question text to ask the target agent

| `timeout`
| no
| 120
| Timeout in seconds (10 to 600)
|===

The tool returns plain text containing the target agent's response.

**Important constraints:**

* The target session must be idle.
If the target is working, waiting, or in any non-idle state, the tool returns a "session busy" error without disrupting the target.
* Each request uses a unique UUID for its temporary files, so multiple concurrent ask operations do not conflict (though only one can target the same session at a time).
* All temporary files are cleaned up after the exchange completes, whether it succeeds, times out, or encounters an error.

**Example use cases:**

* An agent working on a frontend feature asks the backend session, "What is the expected response format for the /api/users endpoint?" and gets an answer grounded in that session's full codebase context.
* A session that encounters a failing test asks the session that recently modified the tested module, "What did you change in the authentication flow and why?"
* A coordinating agent asks multiple idle sessions for their assessment of a proposed architecture change, collecting diverse perspectives.

== Session Identification

Sessions are identified by their display name in all tool calls.
If two sessions share the same display name, the tool returns an error listing the ambiguous matches with their pane IDs.
You can then retry the call using the specific pane ID instead of the name.

For example, if two sessions are both named "api-server", calling `cc_deck_read_scrollback` with `session: "api-server"` returns an error like:

[source,json]
----
{"error": "ambiguous session name 'api-server', matches: [pane 42: 'api-server', pane 55: 'api-server']"}
----

Retrying with `session: "42"` targets the specific pane.

== Error Handling

All four tools follow consistent error patterns:

* **Session not found**: Returns an error with the requested identifier when no matching session exists.
* **Plugin not running**: Returns an error when the MCP server cannot reach the cc-deck Zellij plugin via pipe messages.
* **Ambiguous name**: Returns an error listing all matching sessions with pane IDs for disambiguation.
* **Session busy** (cc_deck_ask only): Returns an error when the target session is not idle, without disrupting it.
* **Timeout** (cc_deck_ask only): Returns a timeout error and cleans up temporary files when the target does not respond within the configured period.
