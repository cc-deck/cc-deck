= Multi-Agent Setup
:description: Configure cc-deck to work with multiple AI coding agents

cc-deck supports multiple AI coding agents through a pluggable Agent interface.
Each agent gets automatic detection, hook installation, and event translation.

== Supported Agents

[cols="1,1,2"]
|===
| Agent | Indicator | Integration Method

| Claude Code
| `[CC]`
| Hook entries in `~/.claude/settings.json`

| OpenCode
| `[OC]`
| TypeScript plugin in `~/.config/opencode/plugins/cc-deck.ts`

| Codex CLI
| `[◆]`
| Hook entries in `~/.codex/hooks.json`
|===

== Installing Hooks

The `plugin install` command auto-detects all installed agents and configures hooks for each.

[source,bash]
----
cc-deck config plugin install
----

To install hooks for a specific agent only:

[source,bash]
----
cc-deck config plugin install --agents opencode
----

== Checking Status

View which agents are detected and whether their hooks are installed:

[source,bash]
----
cc-deck config plugin status
----

The output shows each agent's detection state, hook installation state, and configuration path.

== Uninstalling Hooks

Remove hooks for all agents:

[source,bash]
----
cc-deck config plugin remove
----

Remove hooks for a specific agent:

[source,bash]
----
cc-deck config plugin remove --agents opencode
----

== Sidebar Indicators

When sessions from multiple agent types are active, the sidebar shows agent indicators before each session name.
For example, `[CC] api-server` and `[OC] frontend`.

When all sessions use the same agent type, indicators are hidden to save horizontal space.

== Custom Integrations

Use `cc-deck hook --raw` to send pre-normalized JSON payloads from any external process:

[source,bash]
----
echo '{"hook_event_name":"SessionStart","agent":"custom","pane_id":1,"session_id":"s1"}' | cc-deck hook --raw
----

The `--raw` flag accepts the normalized payload format directly, skipping agent-specific translation.
This allows any tool to feed events into the cc-deck sidebar.

== Hook Command

Each agent's hook installation registers a command that calls `cc-deck hook --agent <name>`.
The agent adapter translates the agent-specific payload into the normalized format before forwarding to the Zellij plugin.

[source,text]
----
Agent emits event --> cc-deck hook --agent <name> --> TranslateEvent() --> NormalizedPayload --> Zellij pipe --> Sidebar
----

[#codex-shared-daemon]
== Codex Shared Daemon

Since Codex 0.157, an interactive `codex` client no longer runs its sessions in its own process.
It hands the work to a shared app-server daemon, one per Codex home, and Codex runs its lifecycle hooks inside that daemon.
The daemon carries the environment of whichever client started it first, including the Zellij pane and Zellij session of that client.
Every hook event from every later Codex client therefore names the pane of the first client.
Taken at face value, that inherited identity would hide a new Codex session from the sidebar or put it in the row of another pane.

cc-deck handles this case without any action on your part.
You do not change how you start Codex, the Codex configuration, or the hook installation.

=== How cc-deck Attributes Daemon Events

When the hook command runs, it first checks whether it runs inside the daemon.
This is the case when the managed `codex app-server` daemon, or one of its helper processes, is among its ancestor processes.
An app-server that a tool starts for itself, such as the one an IDE extension runs, is not the shared daemon, and its hooks take the regular path.
For such a daemon-hosted event, cc-deck ignores the pane identity that the hook inherited and looks for the Codex client that owns the event's session:

. *Remembered client.*
When cc-deck has already attributed the session, it reuses the remembered client, identified by its process ID and start time.
The mapping stays valid only while that exact process still runs in the same pane and the same Zellij session.
When that client has exited, cc-deck drops the remaining events of the session until Codex starts or resumes it again, because a different client in the same directory does not own the session.
. *Discovered client.*
Otherwise, cc-deck looks for the single Codex process of the same user and the same Codex home (`CODEX_HOME`, default `~/.codex`) whose working directory equals the working directory of the event.
The working directory of a client is the `-C` or `--cd` argument when one is given, and otherwise the actual working directory of the process on Linux and its `PWD` environment variable on macOS.
cc-deck resolves symbolic links on both sides, so `/tmp` and `/private/tmp` on macOS match.
When no client matches, or several do, cc-deck drops the event and tries again on the next event of the session.

Once cc-deck has found the client, the event goes to the pane and Zellij session of that client.
This holds even when the daemon was started from another Zellij session or from a plain terminal.
The sidebar also shows the profile name and color of the client, so a session started through a profile wrapper such as `codex-team` keeps its own profile.
Codex clients that run outside Zellij never appear in any sidebar.

Only interactive clients receive a sidebar row: plain `codex`, `codex resume`, `codex fork`, and `codex "<initial prompt>"`.
However, every Codex process in the directory counts when cc-deck decides whether the match is unique, including non-interactive runs such as `codex exec` and the app-server of an IDE extension.
The rule behind this is strict on purpose: cc-deck would rather show no row than a wrong one.

=== Several Clients in One Directory

When two or more Codex clients share a working directory and a Codex home, the hook cannot tell which of them started a new session.
New sessions in that directory stay hidden until only one client remains there.
Sessions that already have a row keep updating it, because cc-deck remembers which client owns them.
The same memory has one blind spot: when you resume a session in a second client in the same directory while its original client still runs, the session keeps the row of the original client.
A second blind spot concerns a session that never received a row because its directory was shared.
When its client exits while the session still sends a few final events, and only one other client remains in that directory, those final events can briefly appear in the row of the remaining client.

[TIP]
====
Give each Codex client its own working directory, for example one Git worktree per agent.
If several clients must share a directory, start them with `codex --no-daemon`, which runs the hooks in the client process itself.
====

=== Codex Without the Daemon

When Codex runs without the shared daemon, the hooks run inside the client process and carry the pane identity of that client.
This applies to `codex --no-daemon` and to Codex releases older than 0.157.
Attribution then uses the pane identity of the hook process directly, just as it does for Claude Code and OpenCode.

=== Platform Support

Finding the originating client requires inspecting the process table, which cc-deck supports on macOS and Linux.
On Linux, cc-deck reads the environment of each Codex process, which the kernel refuses for a process that marks itself as non-dumpable, so cc-deck drops daemon-hosted events of such processes.
When cc-deck cannot inspect the processes of the hook, on other platforms or after an inspection error, it drops Codex events instead of guessing a pane.

=== Diagnosing Attribution

When a Codex session does not show up in the sidebar, enable the hook debug log and reproduce the problem:

[source,bash]
----
touch ~/.local/state/cc-deck/hook-debug
tail -f ~/.local/state/cc-deck/hook.log
----

Each Codex event then records how cc-deck determined the pane or why it dropped the event, for example `resolution=discovered` or `resolution=ambiguous`.
Remove the flag file when you are done, because the log grows with every hook event.
See xref:reference:cli.adoc#hook-debug-log[the `hook` command reference] for the flag file, the log fields, and the full list of resolution values.

[#claude-code-background-sessions]
== Claude Code Background Sessions

Claude Code can park an interactive session with `/background`, start a job with `claude --bg`, or view a running job with `claude attach <jobId>`.
Background jobs run in a daemon whose environment belongs to the terminal that first started it.
cc-deck finds the terminal that currently views each job and sends the job's events to that pane, including when the viewer uses another workspace.
You do not need to change your Claude Code settings or reinstall hooks for this attribution.

A background row shows a dim `⇣` before its name.
The status indicator still reports working, waiting, or done, and a manual rename survives the move to the background.
The marker disappears with the next foreground event.

cc-deck recognizes two kinds of viewer: a parking terminal whose session record still names the job in `parkedJobId`, and a `claude attach` process naming the job.
Both must use the same Claude Code configuration directory as the worker, even when profiles share their session-record directory.
When both processes occupy the same pane, they count as one terminal.
The row uses the viewer's profile name, color, and icon.

A job stays hidden while it has no viewer, several viewer terminals, or a single viewer outside the workspace.
Each job event checks the viewers again, so the row resumes updating when exactly one workspace pane views it.
When that viewer moves or detaches, the next event releases the former row if it still belongs to the job.
A different agent or conversation that has taken the pane keeps its row.
Attaching to an idle job updates the sidebar only after the job emits its next hook event.

[NOTE]
====
In the tested Claude Code 2.1.302 release, `/background` exits the original terminal interface and leaves no `parkedJobId` viewer.
The job becomes headless until you view it with `claude attach <jobId>`.
cc-deck also supports releases that keep a parking terminal open and name the job in `parkedJobId`.
====

If a background session stays hidden, resume the conversation in the foreground or attach to the job from one workspace pane.
Enable `~/.local/state/cc-deck/hook-debug` and inspect `~/.local/state/cc-deck/hook.log` to see `background=true`, the job ID, and the resolution reason.
The xref:reference:cli.adoc#claude-background-attribution[hook reference] describes each reason and the row-release message.
The upstream report https://github.com/anthropics/claude-code/issues/102949[anthropics/claude-code#102949] tracks terminal identity inherited by background jobs.
